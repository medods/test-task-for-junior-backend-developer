# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Swagger

Базовый префикс API:

## Реализация периодичности

### Декомпозиция задачи

Перед реализацией фичи были рассмотрены два принципиально разных подхода:
- Хранить периодичность как атрибут задачи
- По расписанию создавать новые экземпляры задачи (нужен фоновый воркер)

В целом, оба имеют как свои плюсы, так и минусы. От второго подхода было решено отказаться и вот почему:

Клиент создает задачу -- она имеет уникальный ID, задает повторяемость, при достижении необходимой даты создается 
новый экземпляр задачи -- новый уникальный айди, причем создается та же самая сущность -- у нее также должны быть параметры повторяемости.

На этом этапе у нас уже две задачи, что произойдет при достижении новой даты ? -- Каждая из них реплицируется.
Можно добавить какой-то флаг или вовсе создать новую сущность "ребенка" с фиксированной периодичностью и отсутствием репликации.

С точки зрения медперсонала, который пытается разобраться, откуда у него взялась новая задача и почему он не может на ней изменить периодичность,
эта функция банально неудобна и избыточна:
- А если повторяемость ежедневная ?
- А если, потенциально, каждые несколько часов ?
- Как искать оригинал, если его надо удалить ? Что станет с его детьми ? Их удалять каскадно ?
- Создавать отдельные вкладки под детей/родителей ?
- При создании экземпляра удалять родителя ? Зачем тогда вообще нужны экземпляры ?
- ...

Реализация фичи с этим подходом в текущем контексте модуля имеет много неопределенностей и потенциально создает лишнюю нагрузку на бд,
поэтому было принято решение реализовать периодичность в качестве нового параметра для объекта задачи.

### Как это работает

Периодичность как атрибут задачи -- опциональный, NULL для одноразовых задач без повторения. Это не одно поле, а несколько взаимоисключающих типов с разными параметрами:
```go
type Recurrence struct {
	Type          RecurrenceType `json:"type"`                     // тип периодичности
	IntervalDays  *int           `json:"interval_days,omitempty"`  // параметр "каждые N дней"
	MonthDay      *int           `json:"month_day,omitempty"`      // конкретный день каждого месяца
	SpecificDates []time.Time    `json:"specific_dates,omitempty"` // список указанных дат
	EvenDays      *bool          `json:"even_days,omitempty"`      // четные/нечетные дни
}
```
Если тип периодичности не совпадает с указанным параметром или в сам параметр некорректный -- клиенту вернется ошибка.

Валидация с проверкой консистентности полей под каждый тип реализована на уровне домена.

### Как хранить

Есть два варианта:
- Отдельная таблица `task_recurrence` со связью по `task_id`
- JSONB колонка `recurrence` прямо в `tasks`

Был выбран второй вариант: проще, не нужны джоины, структура периодичности достаточно простая, ее легко читать и взаимодействовать с ней.

Также возможен GIN индекс на JSONB, если потребуется фильтрация по типу периодичности.

### Проблема ежемесячных задач

В условии сказано, что ежемесячные задачи ставятся на каждое определенное число месяца: от 1 до 30. 
Проблема в том, что в некоторых месяцах может быть 31 день, а в феврале 28/29 дней. 

Для удобства клиента было принято решение допустить значения от 1 до 31 включительно. 
Если в месяце дней меньше, чем указано в задаче -- задача выполняется в последний день месяца. 

Реализация этой логики выходит за рамки ответственности нашего модуля -- мы храним настройку, а не управляем ей. 
Заниматься этим должен планировщик.

### Планировщик

Это отдельная система, которая использует настройки нашего модуля.

Как было уже сказано ранее, он определяет, в какой день задача должна повторяться:
```go
RepeatAt := min(MonthDay, LastMonthDay) // псевдокод
```
Помимо этого, планировщик должен заниматься актуализацией задач, то есть в списке активных задач на сегодня (или любой другой день)
должны отображаться только те задачи, которые были заданы на него или должны в этот день повториться.

То есть, это должен быть отдельный модуль/микросервис, в чью ответственность входит только управление задачами,
полученными через API трекера задач. Общаться они могут через брокер сообщений, например, Kafka.

### Пример создания задач 

#### Одноразовая задача
```json
// Request body
{
  "title": "Выписка пациента",
  "description": "Выписать пациента из 242 палаты",
  "status": "new"
}
```

```json
// Response body: 201
{
  "id": 1,
  "title": "Выписка пациента",
  "description": "Выписать пациента из 242 палаты",
  "status": "new",
  "created_at": "2026-04-22T13:56:25.172941Z",
  "updated_at": "2026-04-22T13:56:25.172941Z"
}
```
#### Задача с ежедневной периодичностью
```json
// Request body
{
  "title": "Обход пациентов",
  "description": "Обойти всех пациентов левого крыла на 2 этаже",
  "status": "new",
  "recurrence": {
    "type": "every_n_days",
    "interval_days": 1
  }
}
```
```json
// Response body: 201
{
  "id": 2,
  "title": "Обход пациентов",
  "description": "Обойти всех пациентов левого крыла на 2 этаже",
  "status": "new",
  "created_at": "2026-04-22T14:01:59.555298Z",
  "updated_at": "2026-04-22T14:01:59.555298Z",
  "recurrence": {
    "type": "every_n_days",
    "interval_days": 1
  }
}
```

#### Некорректные параметры периодичности
```json
// Request body
{
  "title": "Подписать отчетность",
  "description": "Отмечаться в отчетности каждый четный день",
  "status": "new",
  "recurrence": {
    "type": "even_odd_days",
    "month_day": 20
  }
}
```
```json
// Response body: 400
{
  "error": "invalid task input: invalid recurrence"
}
```

#### Несуществующая периодичность
```json
// Request body
{
  "title": "Смена дежурства",
  "description": "Каждые 4 часа сменять дежурного",
  "status": "new",
  "recurrence": {
    "type": "every_n_hour",
    "interval_hours": 4
  }
}
```
```json
// Response body: 400
{
  "error": "json: unknown field \"interval_hours\""
}
```
