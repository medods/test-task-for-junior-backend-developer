# Task Service

Сервис для управления задачами с HTTP API на Go.

Поддерживает задачи без расписания и задачи с периодичностью.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Периодичность

Поле `period` в `POST/PUT /api/v1/tasks` необязательное.

Поддерживаемые типы:

- `daily` - каждые `interval_days` дней, начиная с даты создания задачи
- `monthly` - в `month_day` число месяца, допустимы значения `1..30`
- `specific` - только в даты из `specific_dates`
- `even_odd` - только в чётные или нечётные дни месяца через `even_odd_type`

Пример создания ежедневной задачи:

```json
{
  "title": "Обзвон пациентов",
  "description": "Повторный контакт после выписки",
  "status": "new",
  "period": {
    "type": "daily",
    "interval_days": 2
  }
}
```

Пример создания задачи на конкретные даты:

```json
{
  "title": "Инвентаризация",
  "description": "Проверка расходных материалов",
  "period": {
    "type": "specific",
    "specific_dates": ["2026-04-24", "2026-04-30", "2026-05-12"]
  }
}
```

## Принятые предположения

- Периодическая задача хранится одной записью, а поле `scheduled_date` вычисляется динамически как ближайшая следующая дата выполнения. Отдельный фоновый генератор экземпляров задач не добавлялся, потому что его в исходной архитектуре нет.
- Для `daily` точка отсчёта равна моменту создания правила. Если меняется только заголовок, описание или статус, расписание не сдвигается. Если меняется само правило периодичности, отсчёт начинается заново с момента обновления.
- Для `monthly` значения `29` и `30` допустимы, но месяцы без такого числа пропускаются. Например, задача на `30` число после `2026-02-15` получит следующую дату `2026-03-30`.
- Для `specific` даты нормализуются, сортируются и дедуплицируются. Если все даты уже в прошлом, задача остаётся валидной, но `scheduled_date` возвращается как `null`.
- Валидация разрешает только поля, относящиеся к выбранному типу периодичности. Остальные входные поля игнорируются на уровне нормализации и не сохраняются.
