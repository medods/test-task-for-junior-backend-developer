# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Анализ существующих решений
Был проведен анализ следующих существующих решений:
- `Google Calendar`
- `Xiaomi Календарь`
- `Jira`
- `Trello`
- `Epic Systems`
- ` Cerner (Oracle Health)`

Из рассмотреных решений было решено воссоздать возможность устанавливать количество повторений (`repeat_count`).
Почти все решения построенны на связи шаблон → экземпляры, поэтому данный подход был использован в данной реализации.
Существующие решения не имеют системы отслеживания дубликатов созданных задач,
поэтому отслеживание создание дубликатов задач и шаблонов щадач остается на совести пользователя.

## Что было реализовано

В рамках реализации тестого задания была добалена возможно установки переодичности для задач путем создания родительского шаблона,
по средствам которого создаются задачи.
Задача также может быть создана без указания переодичности и будет являться обычной единоразовой задачей.

Шаблон является структурой `RecurrenceConfig`, является частью структуры `Task` (Экземпляр задачи) и определяется флагом `IsRecurringTemplate` отмечающим его как родительский шаблон
для создаваемых задач. Каждая созданная по шаблону задача имеет указатель на свой родительский шаблон (`parent_template_id`). 
Данные о шаблоне хранятся в структуре `Task` с формате JSONB, что является гибким решением для работы с общими данными и поддерживает будущие расширения 
сценариев для периодичности.

Реализованные типы переодичности:
- `Daily` - ежедневные задачи с переодичностью в задаваемое пользователем значение.
- `Monthly` - ежемесячный тип задач, привязанный к дате в месяца.
- `SpecificDates` - задачи с конкретно установленными датами.
- `ParityDates` - задачи создаются либо только на четные числа, либо только на нечетные. 

## Ограничения
Для параметра генерации (`repeat_count`), были установлены ограничения генерации для каждого из типов переодичности:
- `Daily` - не более 365
- `Monthly` - не более 24
- `SpecificDates` - не более 100 дат
- `ParityDates` - не более 365

В реализации нет возможности проверять создаваемые шаблоны и задачи на дубликаты (абсолютно совпадающие параметры), за исключением 
работы с периодичностью `SpecificDates`. Если в перечислении дат `SpecificDates` встречаеются дубликаты дат, они игнорируются и создается лишь одна задача с дублированной датой.

## Особенности
В реализации ежемесячного типа `Monthly` я немного отошла от заявленного ограничения из ТЗ (1-30). 
Мной выбрано ограничение покрывающе все возможные даты (1-31). В случиях когда выбранной даты нет в месяце (например `30 февраля`) задача будет сгенерирована на крайнее число месяца (`28/29 февраля`).

У пользователя есть возможность установить количество задач, которое необходимо создать с выбранной периодичностью. (Пример: 10 капельниц каждые 2 дня).
Устанавливается количество с помощью параметра: `repeat_count`.
У каждого типа переодичности установлено дефолтное значение генерации в случае, если пользователем оно не было установлено.

- `Daily` - 90 (дней)
- `Monthly` - 24 (месяца)
- `SpecificDates` - дефолтное значение пустое, т.к. для создания необходимо указать хотя бы одну дату
- `ParityDates` - 90 (дней)

Создаваемые по шаблону экземпляры задач являются зависимыми к нему.
При редактировании шаблона будут изменяться экземпляры задачь путем пересоздания с новыми данными,
однако те экземпляры, которые уже были выполнены и имею статус `done` не изменяются и сохраняют свои изначальные параметры. 

При редактировании же экземпляра задачи созданной по шаблону, шаблон никак не будет изменятся, т.к. не является созависимым.

## Предложения
В будущем к данной реализации можно было бы добавить следующие доработки:
- Добавить дату окончания для создания экземпляров задачи в дополнение к `repeat_count`
- Добавление нескольких временных точек. На данный момент, задачи создаются на одно и тоже время указанное при создании шаблона, без возможности создать в один день несколько задач одного шаблона.
- Поддержка более сложных правил переодичности. (Например: конкретные дни недели)
- Улучшение системы редактирования (`Update`). На данный момент, чтобы отредактировать задачу или шаблон необходимо передавать все их параметры.
Возможность передавать только те данные, которые пользователь хочет изменить, значительно улучшило использование.
- Установка приоритета на задачах. Для выделения пользователю, какая из задач требует его особого внимания.
